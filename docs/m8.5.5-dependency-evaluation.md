# M8.5.5 PDF/图片依赖与 Windows 渲染路径评估

日期：2026-08-10

## 结论

- 图片/漫画先行：优先评估 Rust 原生 image 解码链，只启用 PNG、JPEG、GIF、WebP 等当前探测范围，关闭不需要的默认格式和并行特性。
- PDF 暂不导入：继续使用现有只读探测。PDF 解析、文本层和渲染属于不同能力，不能因为能读取版本号就承诺阅读。
- Windows WebView2 只作为候选渲染容器，不作为当前 PDF 数据模型的唯一实现。必须先证明页码、目录、搜索和进度回写能够稳定受控。
- 公开安装包默认只接受可公开再分发、许可证清晰、能在 GitHub Actions 中复现的依赖；任何动态 PDF 库都必须额外提交二进制、NOTICE、版本和供应链记录。

## 候选比较

| 候选 | 能力 | 发布/维护风险 | 决策 |
| --- | --- | --- | --- |
| image Rust crate | 常见图片格式解码、尺寸和像素读取；Apache-2.0/MIT；支持关闭默认 feature 后按格式启用 | 解码仍可能产生大像素缓冲，必须在读取前做像素/字节配额；需要补充损坏图片夹具 | 图片首选候选 |
| lopdf | MIT（仓库说明另有 Montserrat 字体例外）；PDF 对象、目录和文本结构处理 | 本身不是页面渲染器，内存模型偏向将文档对象保留在内存；不能独立提供高质量 Windows 页面显示 | 仅作为未来 PDF 元数据/文本层候选，不引入 |
| pdfium-render + Pdfium | 可渲染页面、提取文本/图片和访问目录；Rust wrapper | wrapper 不构建 Pdfium，需自行提供动态库或静态库；Pdfium 非线程安全，wrapper 通过互斥保护；Windows DLL、ABI、版本、NOTICE 和发布体积均需治理 | 暂缓，待供应链/二进制发布评估 |
| WebView2 内置 PDF viewer | Windows 上可利用 Edge/WebView2 的 PDF 显示能力 | WebView2 的 PDF viewer 是浏览器功能，阅读器自有页码、目录、搜索、进度和恢复模型仍需验证；不能把浏览器 UI 当成后端数据模型 | 仅作实验性渲染路径，不作为当前导入承诺 |
| PDF.js 或其他 JS viewer | 可在 WebView2 内部自定义页码、搜索和目录 | 增加前端资源、内存和许可证清单；需要安全地提供本地文件并阻止外链/脚本越权 | 后续候选，不在本切片引入 |

## 证据与来源

- image-rs 官方仓库列出 Apache-2.0/MIT 许可证、常见格式和 feature flags，并建议发布库关闭 default-features 后按需启用：
  https://github.com/image-rs/image
- lopdf 官方仓库说明其为 MIT（Montserrat 字体除外），并提供 PDF 对象流与文本/文档处理，而非通用页面渲染：
  https://github.com/J-F-Liu/lopdf
- pdfium-render 官方文档说明 Pdfium 需要单独提供，wrapper 不替用户构建；同时提示 Pdfium 没有线程安全保证：
  https://github.com/ajrcarey/pdfium-render
- Chromium Pdfium 的 LICENSE 同时包含 BSD 风格条款与 Apache License 2.0，公开发布时需要保留相应版权、许可和 NOTICE：
  https://github.com/chromium/pdfium/blob/main/LICENSE
- Microsoft WebView2 官方文档列出 PDF viewing 已启用，但 PDF annotations 在 WebView2 中关闭；因此仍需做应用级页码/搜索/恢复能力验证：
  https://learn.microsoft.com/en-au/microsoft-edge/webview2/concepts/browser-features
  https://learn.microsoft.com/en-us/microsoft-edge/webview2/

## 统一采用闸门

任何依赖进入 Cargo.toml 或前端资源前，必须同时满足：

1. Cargo license、传递依赖和二进制组件逐项记录；动态库附版本、来源、哈希和 NOTICE。
2. Windows Release、Linux Rust checks 和离线 smoke 在 GitHub Actions 可重复；不依赖开发机全局安装。
3. 输入文件、解码像素、并发页数、缓存大小和单页耗时都有硬上限。
4. 损坏、截断、超尺寸、加密/受保护输入能够单页失败或明确拒绝，不造成书架或进度丢失。
5. 取消、重试、缓存淘汰和进度恢复都能映射到 M8.5.4 的 ReaderDocumentEnvelope。

## 已完成与下一项实现

M8.5.5a/b/c/d1 已完成并通过远程验证：

- M8.5.5a 以受限 feature 引入 `image 0.25.9` 解码链，只返回安全的 ImageDocument 元数据和单页预览句柄；PNG/JPEG/GIF/WebP 的像素总量、解码字节、MIME、损坏尾部和超尺寸夹具已通过。
- M8.5.5b 在不信任前端原始路径、URL 或伪造元数据的前提下，建立图片序列 `ltr`/`rtl`/`vertical` 方向和 `single`/`double`/`long_strip` 排版模型，并限制 2,048 页、128,000,000 总像素、512 MiB 总解码字节。
- M8.5.5c 新增批量图片预览命令：逐页复用单图解码闸门，限制原始输入总量 256 MiB；前端支持多选图片、最多 24 个临时缩略图、方向切换和排版模式切换，仍不写入书架。
- M8.5.5d1 为每个图片页生成内容摘要并组合为不含绝对路径的序列缓存键；前端在本机恢复页码、缩放、方向和排版，当前只保存位置元数据，不写入书架或磁盘缩略图。
- GitHub Actions run [31350842759](https://github.com/TttXxx36/Open-reader-desktop/actions/runs/31350842759)、[31351541210](https://github.com/TttXxx36/Open-reader-desktop/actions/runs/31351541210)、[31352828101](https://github.com/TttXxx36/Open-reader-desktop/actions/runs/31352828101) 与 [31353873233](https://github.com/TttXxx36/Open-reader-desktop/actions/runs/31353873233) 均通过 Rust、前端和 Windows 编译/峰值 RSS 采样；本地不构建、不安装。

下一项是持久化缩略图文件缓存、取消/重试和缓存失效：

- 将现有内容摘要缓存键映射到应用数据目录中的缩略图文件，采用临时文件加原子替换并受容量/LRU 限制；文件路径不由前端提供。
- 增加取消/重试、页序调整、当前页/相邻页恢复、缓存失效和崩溃恢复夹具；暂不写入书架，直到数据库迁移和恢复测试完成。
- PDF 仍独立评估解析、渲染、搜索、目录、供应链和受保护内容拒绝，不在此切片引入。
